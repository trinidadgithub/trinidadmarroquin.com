# Nimble PVC cleanup tooling: evidence and improvement review

## Scope and evidence

Read-only review of `Virginia-IAD/Check PVC Volume Status.pdf`, the working `nimble_pvc_cleanup.py` and `run_remaining.py`, their bundled README/copies, `nimble-cleanup-evidence/` listings/CSV files, `nimble-review/` approvals/manifests, and the separately stored `delete-batch-001.csv`. This is analysis of source and archived records, **not** a live-array test or a change to the scripts. The working `run_remaining.py` and bundled wrapper have identical hashes; the working base script differs slightly from bundled copies (the initial bundled version uses `BatchMode=yes`, while the working copy uses `BatchMode=no`). Confirm the precise pair deployed in any future run.

## Reconciled result and a corrected interpretation

The initial `nimble-vol-list.txt` contains 1,209 PVC rows (nine online, 1,200 offline/User); `nimble-final-inventory.txt` contains 11 (nine online, two offline). The initial and final online-name sets match. `offline-pvc-deletion-manifest.csv` has 1,200 rows. The remainder dry-run journal has **1,172** `dry_run,pass`, **25** `check,missing`, and **two** `check,skipped` (snapshots). The final approved-name set is identical to the 1,172 pass names; `remaining-delete.csv` has 1,172 `delete_intent,started` and 1,172 `delete,success` rows, with no recorded skips or halts. None of those 1,172 names remains in the final listing.

Crucially, **all 25 `missing` names match the 25 `delete,success` rows in `delete-batch-001.csv`**. The canary has a separate one-row `delete-001.csv`. The three sets do not overlap, and their union equals the 1,198 PVC names present initially and absent finally: **1 canary + 25 earlier batch + 1,172 later bulk**. The PDF initially speculates about the 25; its earlier-batch journal establishes their recorded disposition. They were *not* deleted by the bulk wrapper. The two preserved offline volumes each had 1,020 snapshots in the PDF's `vol --info` outputs and are both present in the final listing. No independent array audit of their snapshot purpose or physical capacity change was supplied.

## What the inspected code actually does

| Behavior | Implementation and boundary |
| --- | --- |
| Listing/manifest | `nimble_pvc_cleanup.py:20–33` (`parse_list`) recognizes syntactically valid PVC rows and rejects duplicate parsed names; `inventory:61–85` filters offline/User and initializes approvals only if absent. Other malformed PVC lines are silently ignored. |
| Authentication | Original bundled `remote()` uses `BatchMode=yes`; working `remote:36–44` uses `BatchMode=no`. `run_remaining.py:14–23` invokes SSH with `BatchMode=no` and a 15-second connect timeout. Captured output is checked for exit code and selected error patterns. |
| Canary safeguards | `execute:88–165` checks manifest/approval membership, `vol --info` state, connections, snapshots, collection, protection, clone, ACL and size where present; requires `--execute` plus exact `DELETE-<host>-<selected-batch-length>`. It does **not** verify ownership or retention. |
| Canary postcheck flaw | `execute:151–158` maps **every** `RuntimeError` from the post-delete `vol --info` to an empty result and logs success. Authentication, network or CLI errors can be mistaken for deletion. An independently successful `vol --list` was used for the actual canary. |
| Bulk scope and live checks | `run_remaining.py:68–90` validates headers, manifest states/sizes, approvals and prior successes. `main:93–115` captures a listing per group; per volume it checks listed online/offline state and size, then `vol --info` with `check_info:41–55`. No Kubernetes ownership/retention check exists in code. |
| Bulk delete/verification | `main:116–129` writes `delete_intent`, issues `vol --delete`, requests a fresh `vol --list`, checks the target is absent, then writes `delete,success`. Absence from a *successfully fetched, correctly parsed* listing is the code's proof, not an independent array audit. |
| Stop/skip behavior | `main:100–108,131–137` skips missing/unsafe items; recognized transport/auth failures and uncertain deletes halt. `nimble_pvc_cleanup.py:160–165,172` stops on error by default; its `--stop-on-error` is `store_true` with default `True`, so it cannot be disabled through the CLI. |
| Resume journal | `run_remaining.py:25–39,85–90` appends CSV rows, flushes per row, reads existing `delete,success` entries and removes those names from remaining work. It does not validate complete row schema, unique successes, prior authorization provenance or current array state for those successes. |

`check_info()` requires zero snapshots/locked snapshots, `Protected: No`, `Volume collection: none/N/A`, `Clone: No`, zero connections, empty parsed ACL and an exact size match. `inspect()` takes only unindented `key: value` lines: an indented continuation under `Access Control List` or `Connected Initiators` is not verified separately. The utility's checks are useful filters, not an ownership or no-dependent-data proof.

## Findings and improvements for a future version

1. **Treat post-delete uncertainty as a halt, never success.** The original script's `except RuntimeError: after=''` is unsafe. Replace it with a typed `not found` result distinguished from SSH/CLI failure, and require an independently successful complete listing or array API response before `success`. The wrapper is an improvement but still relies on a permissive listing parser: if the target's line is malformed or a truncated listing contains other PVCs, `name not in after` can misclassify it. Validate completeness and corroborate uncertain results through another query/audit.
2. **Classify errors by source.** `run_remaining.ssh()` treats exit 255 or selected output patterns as `InfrastructureError`; other nonzero statuses and CLI `ERROR:` become `UnsafeVolume`. Thus some array-wide failures can be skipped as if isolated volume failures. Its `UncertainDeletion` covers array errors *after* issuing delete and failures in postcheck, but a transport exception from `ssh()` after the delete has been sent is handled as infrastructure halt without an explicit per-volume uncertain result. Record phase, exit status and uncertainty separately; investigate the last intent before resume.
   A parser exception from the post-delete listing is not handled by the wrapper's typed exception branches; it can leave an intent without a structured halt row. Test these failure paths without connecting to the array before reusing the script.
3. **Pin the scope and detect drift.** A manifest holds inventory-time size/state, not immutable identity or cluster ownership. `run_remaining.py` checks live name, size and state, but no unique array ID/serial or authorization record. Capture and compare immutable volume identity, bind approved scope to a signed/versioned change record, refuse unreviewed approval edits, and fail closed if the listing is incomplete. Preserve historic manifests rather than overwriting them without reconciliation.
4. **Harden journaling and resumption.** A flushed CSV row is not an fsync/transaction; a crash can leave a partial row or a delete intent without success. `read_success()` only validates headers, so truncated or forged rows could be misread or trusted; a manually changed approval list or journal can change resume semantics. Validate each row, sequence, unique names, approved-set digest, host/array identity and journal integrity. On resumption independently reconcile *every* uncertain intent and, ideally, re-check previously successful names against the array before reporting completion. Never count `missing` as a delete success.
5. **Define concurrency and pacing.** There is no lock on approval files or journals and no array-side concurrency coordination. The wrapper's `--pause` is optional and defaults to zero; 25 is a grouping size, not a request-rate limit. Use exclusive locks, one change owner, array health monitoring, configurable pacing/backoff, and a stop gate on throttling or transport instability.
6. **Retain snapshot and ownership exceptions.** An offline volume can still have snapshots or belong to another workload. The two preserved volumes have 2,040 snapshots collectively; neither a shared schedule nor their retention purpose was established. Maintain a separate exception register and investigate owners, snapshot/clone dependencies and recovery policy before any future approval.
7. **Improve audit privacy and result semantics.** Journals record remote output/error details and can include usernames, array endpoints or sensitive data; restrict and redact copies for publication. Make summary output separate `deleted_now`, `already_missing_with_prior_evidence`, `skipped_unsafe`, `halted_uncertain`, and `verified_remaining` counts. Report provisioned-size and mapped-usage changes separately from actual physical array free-space change.

## Remaining evidence limits

The saved listing and journals provide strong set-level reconciliation, not an independent storage-controller audit for every historical delete. The PDF shows the operator's final `vol --list` capture and comparison; there is no retained cryptographic chain of custody, per-volume retention sign-off, or before/after physical array free-space metric in the inspected files. The 25 earlier-batch successes reconcile their absence, but the original utility's weak postcheck still makes the **independent later listings** essential. The purpose and ownership of the two snapshot-bearing exceptions require human investigation.
